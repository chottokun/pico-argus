# コグニティブ・フォーカストラッキング・エッジシステム：LLMエージェント統括型「能動的知覚（Active Perception）」詳細設計仕様書（V2・実機稼働見直し版）

本仕様書は、これまでの「受動的・自動的」なカメラ追尾システムにおける根本的な設計矛盾を克服し、**LLM（LangGraph 1.0 / Gemma 4 / Qwen2.5-VL）をシステム全体の絶対的な司令塔（Orchestrator）**として再定義した、真のエージェント主導型詳細設計である。

---

## V1設計（受動的追尾）が孕んでいた「3つの盲点」

1. **YOLOによる主導（受動的対話）**:
   従来のシステムは、YOLOが「人」や「車」を検知した瞬間、カメラがルールベースで勝手に（自動的かつ受動的に）追尾を開始し、LLMはただ「追跡しています」と後追いで発話するだけの受動的な存在に留まっていた。これでは「LLMエージェント」である必要性が希薄である。
2. **常時画像処理によるVRAM/CPUの枯渇**:
   常時画像を重いVLMに入力して「状況変化」を監視し続ける構成は、12GB VRAM等のエッジ環境（RTX 3060/4060等）において、数秒〜数分でメモリ枯渇（OOM）または熱暴走（サーマルスロットリング）を引き起こす物理的限界があった。
3. **視線（PTZ）と解釈（VLM）の不一致（Spatial Disconnect）**:
   広角カメラのままVLMに画像を入力しても、対象（例：人間が手元に持っている鍵や不審物）は数ピクセルの極小領域に潰れてしまい、VLMは「何も持っていない」と誤認（ハルシネーション）していた。

## 1. 常時画像監視を廃止した「時間分割・テキストメタデータ知覚」

エッジPCの処理リソースを極限まで保護するため、**常時画像理解（VLM）を走らせることを完全に禁止**する。

1. **YOLO-ONNX / ByteTrack による常時テキスト化（10ms〜30ms）**:
   常時稼働するのは、VRAM占有量わずか `500MB`、推論時間 `10ms` 前後の極軽量な YOLO + ByteTrack のみ。このエンジンが画面上のオブジェクトを「ID（track_id）」、「クラス名」、「正規化座標」、「移動速度」の**軽量なテキストメタデータ（JSON形式）**へと常時変換し、システムステートの知覚バッファ（`AgentState.active_tracks`）を高速に書き換え続ける。
2. **VLM（Qwen2.5-VL / Gemma 4 12B）の完全スリープとオンデマンド起動**:
   VLM（VRAM約2.9GB）は常時推論を行わず、通常時は完全に処理をバイパス（スリープ）しておく。LLMが「意味的（セマンティック）に詳しく状況を精査する必要がある」と判断した瞬間のみ、オンデマンドで画像をVLMに入力して意味を暴く。

## 2. LLMエージェントによる「能動的知覚（Active Sensing）」自律シーケンス

LLMが意志を持って「自ら見に行き、ズームし、正体を突き止めて記憶（Wiki）に書き込む」という、真のエージェントシーケンスを以下に定義する。

### 2.1 【仮説検証】不審エリア侵入時の「アクティブ・ズーム・スキャン」
YOLOが玄関前などの指定境界エリアに、低確信度のオブジェクト（例：ID: 105、class: 'bag?'、conf: 0.35）を検出したとする。

1. **内省思考（Thinking Mode）による仮説生成**:
   YOLOメタデータから、LLMエージェントは自律的に「玄関前警戒エリアに、YOLOだけでは判別不能な低確信度の物体が存在する。これは不審な置き去り荷物か、単なる風の影か？」という仮説を立てる。
2. **物理ツールコール（物理視線シフト）**:
   LLMが `set_ptz_lock_and_zoom(track_id=105, target_zoom=3.0)` ツールをキックする。PTZコントローラが即座に起動し、カメラを指定ターゲット（ID: 105）に向けて自動旋回。重心を捉えた後、画角面積比20%に達するまで**自動光学ズームで物理的に接近・クローズアップ**する。
3. **スポットVLM解釈（能動的知覚の開眼）**:
   ズームが完了した瞬間の高解像度フレームから、ID: 105の領域だけをピンポイントにクロップし、VLMに入力。LLMが **「このズーム画像を解釈し、何が起きているか詳細を説明せよ」** というビジュアルクエリツールを実行。
4. **結果評価と自律Wikiコンバイル（OKF）**:
   VLMが「これは家主のたかしさんが新しく購入した、黄色の小型フォークリフト用の充電バッテリーである」と高精度に意味同定。LLMはこれを受け、自動で `wiki/known_objects.md` にOKF形式（YAML Frontmatter付き）で「ID 105：たかしさんの新規購入バッテリー、危険度：低」と新規蓄積（学習）する。

## 3. エージェント主導型 LangGraph 1.0 動的ステート＆グラフ設計

LLMを司令塔とするため、LangGraphのグラフノード設計は、LLMが「状態評価（内省思考）➔ ツール実行 ➔ 状態変異 ➔ 再帰プラン」を自律決定できるルーティングにする。

### 3.1 拡張された AgentState スキーマ定義
```python
from typing import TypedDict, List, Optional, Dict, Any

class AgentState(TypedDict):
    # 知覚レイヤー (Perception Buffer)
    active_tracks: List[Dict[str, Any]]   # YOLO/ByteTrackから常時流れ込むリアルタイムメタデータ
    current_frame_path: Optional[str]     # ズーム・スポットクロップ画像の保存先パス
    
    # 物理制御・状態レイヤー (Physical Control)
    lockon_mode: str                      # "auto" (自律配分) | "id" (ID指定ロック) | "preset"
    target_track_id: Optional[int]        # LLMがロックオン（追尾）を命じたオブジェクトの tracker_id
    ptz_dynamic_gain: float               # LLMが適応調整したPIDの比例ゲインベース値
    
    # 認知・長期記憶・対話レイヤー (Cognition & Memory)
    agent_goal: str                      # LLMが現在自律的に設定しているタスク目標
    recalled_knowledge: List[str]         # SQLite FTS5から想起した過去のOKF Wikiルール
    conversation_history: List[dict]      # 対話ログ
    agent_speaking_state: str             # "silent" | "speaking" | "interrupted"
    
    # 割り込み・防衛レイヤー (Failsafe Epoch)
    state_epoch: int                      # 先祖返りを100%防止するためのインクリメンタルなエポック数
```

## V2詳細設計による物理＆論理ガードレールの統合

本設計仕様は、物理デバイス（カメラサーボモーター）の寿命摩耗・突発破壊や、対話時の違和感を技術的に完全に解決するための以下の堅牢化プロトコルを標準搭載する。

1. **エポックベース状態変異（Epoch-Based Guard）による先祖返りの完全抑止** [39, 40]
   ユーザーが緊急割り込み（Barge-In）を入れた瞬間に、動作中だったVLM思考タスク（`asyncio.Task`）に対して `.cancel()` を即座に発行 [40]。同時に、システム全体の `state_epoch` をインクリメント（+1）する [40]。これにより、キャンセル処理をすり抜けて遅れて返ってきた古いVLM推論結果（エポック 0）は、不一致（`0 != 1`）として状態の書き戻し前に安全に完全自動破棄され、競合による「意思決定の先祖返り」を論理的・物理的にゼロ（防衛率100%）にクランプする [39, 40]。
2. **適応型PID制御 ＋ 衝突防止（Dwell Time）＆スルーレート制限による物理負荷保護** [41, 42, 49]
   ONVIFの ContinuousMove は、パケットロス等で Stop コマンドがロストすると壁に激突し続けてモーターを溶融破損させる重大なリスクを孕んでいる [49]。これを防ぐため、すべての物理旋回速度指令に対して **`Dwell Time（350msの自動自律停止）`** をバインドして送信し、かつ限界物理角度での連続駆動時間が5秒を超えた際には強制的に Stop SOAP を発行して物理的に動きを遮断する [43, 49, 50]。
   さらに、急激な起動や急制動によるモーターコイルへの瞬間的な大電流負荷や、物理ギアへの打撃摩耗衝撃を避けるため、制御ステップ出力に **`Slew Rate（スルーレート／加速度）制限`** をバインドする。1ステップあたりの速度変化（増減幅）を `max_acceleration`（デフォルト: `0.03`）以内に制限することで、動き出しを「じわっと滑らかに加速」させ、停止時は「優しく減速して収束」させるソフトスタート・ソフトストップ制御を行い、物理的摩耗を極限まで低減する。
3. **日本語 OKF-Wiki の超軽量 SQLite Trigram 検索** [34, 35]
   VRAMやメインメモリに極大負荷を与えるベクトルDBを一切常駐させず、SQLite 3.34.0以降に標準搭載されている **Trigramトークナイザー（`tokenize='trigram'`）** を採用 [34, 35]。3文字以上の日本語部分一致検索をミリ秒単位で高速実行し、2文字以下の極小ワード（「猫」「タマ」）は LIKE 部分一致検索へ自動で非同期フォールバックさせることで、追加VRAM「ゼロ」での長期記憶想起（RAG）を実現する [34, 35, 36, 37]。
4. **Silero VAD セルフ・バージイン防止 ＆ Flush Trick の将来設計（Phase 4）** [44, 45, 50]
   対話処理を再始動する際、スピーカーから出力される自らの合成音声（TTS）をマイクVADが人間の声と誤認して話し出すたびに自滅的に沈黙してしまう現象を避けるため、**「発話開始から最初の 200〜300ms の間はVAD検知結果を完全に無視する制御ウィンドウ」**を適用 [44, 45]。さらに、VADが無音開始から 100〜150ms 経過したことを検知した瞬間に、一時バッファの音声フレーム（ASR Partials）を即座に強制フラッシュ（Flush Trick）させることで、会話特有のもたつきを完全排除した人間並みにスムーズなキャッチボールを実現する [45]。
5. **共有ビデオリーダー（RTSP シングルトン）によるセッション数制限対策**
   Tapo カメラなどの家庭用IPカメラが持つ厳しい同時接続セッション数制限（上限約2セッション）をクリアするため、知覚モジュール（YOLO検出）と物理制御モジュール（PTZ追従ループ）で別々に RTSP 接続を張ることを完全に禁止する。システム（MCPサーバー等）内に唯一の共有 `RTSPVideoReader` インスタンスをライフサイクル管理し、これを全スレッドやタスク間で安全に使い回すことで、接続の衝突やタイムアウトを物理的にゼロに抑止する。
6. **自動起動モニター（MonitorWindow）による BBox・PID偏差のリアルタイム可視化**
   デバッグの容易化およびリアルタイムのモニタリングのために、別スレッドで OpenCV ウィンドウを自動起動し、映像フレーム上に検出オブジェクト（緑枠）、PIDロックオン対象（太赤枠 ＋ `[LOCKON]`ラベル）、画面中央とターゲット間を繋ぐ制御偏差ライン（および偏差ピクセル数値）を約 30 FPS でオーバーレイ描画する。物理制御の稼働中は、モニターが PTZActuator のアクティブなトラッカーを参照するように自動同期され、描画のフリーズを回避する。
7. **可変レートリミッター（RPMLimiter）によるローカル VLM 負荷調整**
   ローカル VLM（Ollama）の同時推論排他（Semaphore）制御に加え、環境変数 `OLLAMA_MAX_RPM` を介して動的に最大 RPM（Requests Per Minute）を設定可能な `RPMLimiter` を適用する。Ollama の平均処理時間（約 1.87秒）を基準とし、推奨値 `OLLAMA_MAX_RPM=12` にて Ollama の過負荷およびハングを論理的に防止する。
