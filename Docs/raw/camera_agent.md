# コグニティブ・フォーカストラッキング・エッジシステム：LLMエージェント統括型「能動的知覚（Active Perception）」詳細設計仕様書

本仕様書は、**LLM（LangGraph 1.0 / Gemma 4 / Qwen2.5-VL）をシステム全体の絶対的な司令塔（Orchestrator）**として定義し、エッジ環境における高精度なカメラ制御と視覚解析を実現する真のエージェント主導型詳細設計である。

---

## 本システムが解決するエッジAIの「3つの課題」

1. **ルールベース追尾による受動性**:
   従来のカメラシステムは、物体検知のたびに固定ルールで自動追尾を行い、LLMは結果を発話するのみであった。本システムではLLMエージェントが自律的判断に基づいて追尾目標や解釈タイミングを直接制御する。
2. **常時画像処理によるVRAM/CPUの枯渇**:
   常時画像を重いVLMに入力して「状況変化」を監視し続ける構成は、12GB VRAM等のエッジ環境（RTX 3060/4060等）において、数秒〜数分でメモリ枯渇（OOM）または熱暴走を引き起こす物理的限界があった。本システムではYOLOによる軽快な物体追跡とオンデマンドなVLM解釈を分離・連携させる。
3. **視線（PTZ）と解釈（VLM）の不一致（Spatial Disconnect）**:
   広角カメラのままVLMに画像を入力しても、対象（例：人間が手元に持っている鍵や不審物）は数ピクセルの極小領域に潰れてしまい、誤認（ハルシネーション）が発生していた。本システムでは目的領域の高精度ズーム/クロップと視認性確認を連携させて確実な状況認識を行う。

## 1. 常時画像監視を廃止した「時間分割・テキストメタデータ知覚」

エッジPCの処理リソースを極限まで保護するため、**常時画像理解（VLM）を走らせることを完全に禁止**する。

1. **内省思考（Thinking Mode）による仮説生成**:
   YOLOメタデータから、LLMエージェントは自律的に「玄関前警戒エリアに、YOLOだけでは判別不能な低確信度の物体が存在する。これは不審な置き去り荷物か、単なる風の影か？」という仮説を立てる。
2. **物理ツールコール（物理視線シフト）**:
   LLMが `set_ptz_lock_and_zoom(track_id=105, target_zoom=3.0)` ツールをキックする。PTZコントローラが即座に起動し、カメラを指定ターゲット（ID: 105）に向けて自動旋回。重心を捉えた後、画角面積比20%に達するまで**自動光学ズームで物理的に接近・クローズアップ**する。
3. **スポットVLM解釈（能動的知覚の開眼）**:
   ズームが完了した瞬間の高解像度フレームから、ID: 105の領域だけをピンポイントにクロップし、VLMに入力。LLMが **「このズーム画像を解釈し、何が起きているか詳細を説明せよ」** というビジュアルクエリツールを実行。
4. **結果評価と自律Wikiコンバイル（OKF）**:
   VLMが「これは家主のたかしさんが新しく購入した、黄色の小型フォークリフト用の充電バッテリーである」と高精度に意味同定。LLMはこれを受け、自動で `wiki/known_objects.md` にOKF形式（YAML Frontmatter付き）で「ID 105：たかしさんの新規購入バッテリー、危険度：低」と新規蓄積（学習）する。

## V2詳細設計による物理＆論理ガードレールの統合

本設計仕様は、物理デバイス（カメラサーボモーター）の寿命摩耗・突発破壊や、対話時の違和感を技術的に完全に解決するための以下の堅牢化プロトコルを標準搭載する。

1. **エポックベース状態変異（Epoch-Based Guard）による先祖返りの完全抑止** [39, 40]
   ユーザーが緊急割り込み（Barge-In）を入れた瞬間に、動作中だったVLM思考タスク（`asyncio.Task`）に対して `.cancel()` を即座に発行 [40]。同時に、システム全体の `state_epoch` をインクリメント（+1）する [40]。これにより、キャンセル処理をすり抜けて遅れて返ってきた古いVLM推論結果（エポック 0）は、不一致（`0 != 1`）として状態の書き戻し前に安全に完全自動破棄され、競合による「意思決定の先祖返り」を論理的・物理的にゼロ（防衛率100%）にクランプする [39, 40]。
2. **適応型PID制御 ＋ 衝突防止（Dwell Time）＆スルーレート制限による物理負荷保護** [41, 42, 49]
   ONVIFの ContinuousMove は、パケットロス等で Stop コマンドがロストすると壁に激突し続けてモーターを溶融破損させる重大なリスクを孕んでいる [49]。これを防ぐため、すべての物理旋回速度指令に対して **`Dwell Time（350msの自動自律停止）`** をバインドして送信し、かつ限界物理角度での連続駆動時間が5秒を超えた際には強制的に Stop SOAP を発行して物理的に動きを遮断する [43, 49, 50]。
   さらに、急激な起動や急制動によるモーターコイルへの瞬間的な大電流負荷や、物理ギアへの打撃摩耗衝撃を避けるため、制御ステップ出力に **`Slew Rate（スルーレート／加速度）制限`** をバインドする。1ステップあたりの速度変化（増減幅）を `max_acceleration`（デフォルト: `0.03`）以内に制限することで、動き出しを「じわっと滑らかに加速」させ、停止時は「優しく減速して収束」させるソフトスタート・ソフトストップ制御を行い、物理的摩耗を極限まで低減する。
   また、実機キャリブレーション (`calibrate_tapo.py`) によって測定された左右・上下の安全限界値 (`MAX_LIMIT_X` / `MAX_LIMIT_Y`、実機実測例: `±0.89`) を `tapo_config.json` から読み込み、制御ステップの現在位置（論理座標）がこれを超えないように自動クランプ保護を行う。
3. **日本語 OKF-Wiki の超軽量 SQLite Trigram 検索** [34, 35]
   VRAMやメインメモリに極大負荷を与えるベクトルDBを一切常駐させず、SQLite 3.34.0以降に標準搭載されている **Trigramトークナイザー（`tokenize='trigram'`）** を採用 [34, 35]。3文字以上の日本語部分一致検索をミリ秒単位で高速実行し、2文字以下の極小ワード（「猫」「タマ」）は LIKE 部分一致検索へ自動で非同期フォールバックさせることで、追加VRAM「ゼロ」での長期記憶想起（RAG）を実現する [34, 35, 36, 37]。
4. **Silero VAD セルフ・バージイン防止 ＆ Flush Trick の将来設計（Phase 4）** [44, 45, 50]
   対話処理を再始動する際、スピーカーから出力される自らの合成音声（TTS）をマイクVADが人間の声と誤認して話し出すたびに自滅的に沈黙してしまう現象を避けるため、**「発話開始から最初の 200〜300ms の間はVAD検知結果を完全に無視する制御ウィンドウ」**を適用 [44, 45]。さらに、VADが無音開始から 100〜150ms 経過したことを検知した瞬間に、一時バッファの音声フレーム（ASR Partials）を即座に強制フラッシュ（Flush Trick）させることで、会話特有のもたつきを完全排除した人間並みにスムーズなキャッチボールを実現する [45]。
5. **共有ビデオリーダー（RTSP シングルトン）によるセッション数制限対策**
   Tapo カメラなどの家庭用IPカメラが持つ厳しい同時接続セッション数制限（上限約2セッション）をクリアするため、知覚モジュール（YOLO検出）と物理制御モジュール（PTZ追従ループ）で別々に RTSP 接続を張ることを完全に禁止する。システム（MCPサーバー等）内に唯一の共有 `RTSPVideoReader` インスタンスをライフサイクル管理し、これを全スレッドやタスク間で安全に使い回すことで、接続の衝突やタイムアウトを物理的にゼロに抑止する。
6. **自動起動モニター（MonitorWindow）による BBox・PID偏差のリアルタイム可視化**
   デバッグの容易化およびリアルタイムのモニタリングのために、別スレッドで OpenCV ウィンドウを自動起動し、映像フレーム上に検出オブジェクト（緑枠）、PIDロックオン対象（太赤枠 ＋ `[LOCKON]`ラベル）、画面中央とターゲット間を繋ぐ制御偏差ライン（および偏差ピクセル数値）を約 30 FPS でオーバーレイ描画する。物理制御の稼働中は、モニターが PTZActuator のアクティブなトラッカーを参照するように自動同期され、描画のフリーズを回避する。
7. **可変レートリミッター（RPMLimiter）によるローカル VLM 負荷調整**
   ローカル VLM（Ollama）の同時推論排他（Semaphore）制御に加え、環境変数 `OLLAMA_MAX_RPM` を介して動的に最大 RPM（Requests Per Minute）を設定可能な `RPMLimiter` を適用する。Ollama の平均処理時間（約 1.87秒）を基準とし、推奨値 `OLLAMA_MAX_RPM=12` にて Ollama の過負荷およびハングを論理的に防止する。

## 8. AIエージェント運用・行動規範（Agent Operational Rules）

本システムを操作するAIエージェント（LLM）は、以下の手順およびルールを厳格に遵守しなければならない。

1. **直接的な画像ファイルアクセスの禁止 (No Image Direct Access)**:
   - `get_live_snapshot` などのツールによって返された画像ファイルパス（例: `monitor/live_snapshot.jpg`）に対し、AIエージェントがファイル読み込みツール（`view_file` 等）を使用して画像を直接ロードし、自己のビジョン機能で状況を判断・解釈して回答することは**厳重に禁止**する。
   - `get_live_snapshot` は、最終的に「人間のユーザー」に現状のライブ映像を提示するためにのみ使用する。
2. **能動的知覚パイプラインの順守 (Strict Active Perception Pipeline)**:
   - 状況把握や動作確認を行う際は、まず `get_active_tracks` を呼び出してYOLO/ByteTrackが検出したオブジェクトのテキストメタデータ（ID、クラス、座標）を把握する。
   - 次に、詳細な視覚情報を得るために、必ず `analyze_crop_image` に `track_id` や `class_filter` を指定して、プログラム経由でVLM（Ollama）に解析を行わせる。
   - 特定のオブジェクトがない場合（画像全体の状況を知りたい場合）も、`analyze_crop_image` の `track_id` と `class_filter` を両方省略し、`query`（例: "画像全体の様子を詳しく教えてください"）のみを指定して実行することで、VLM経由で画像全体の状況を把握しなければならない。

## 9. 物理カメラ運動方向とONVIF相対移動の符号・極性反転ガイド (Physical Motion Dynamics & Orientation Note)

物理カメラ（Tapo C210 等）の自動追尾において、画面座標系とONVIF物理相対移動（RelativeMove）の運動極性を誤ると、**物体が画面右に移動した際にカメラが左に逃げてしまう負のフィードバック（逆駆動現象）**が発生します。これを防ぐための標準物理仕様と座標系定義を以下に定めます。

### ① 画面正規化座標系 (Screen Coordinates)
- 画面左上: `(0.0, 0.0)` 、画面右下: `(1.0, 1.0)` 、画面中央: `(0.5, 0.5)`
- オブジェクト中心座標:
  $$cx = \frac{x + w / 2}{\text{frame\_width}}, \quad cy = \frac{y + h / 2}{\text{frame\_height}}$$
- 画面中央からの位置偏差:
  $$\text{error}_x = cx - 0.5, \quad \text{error}_y = cy - 0.5$$

### ② 正フィードバック制御の幾何学的運動定義
- **Pan (水平移動)**: オブジェクトが画面の**右側**にいる場合 ($cx > 0.5$)、対象を中央に捉えるためカメラを**右（Pan > 0）**に旋回させる。
- **Tilt (垂直移動)**: オブジェクトが画面の**上側**にいる場合 ($cy < 0.5$)、対象を中央に捉えるためカメラを**上（Tilt Up, cmd_y < 0）**へ物理傾斜させる。

### ③ `tapo_config.json` における極性設定ノウハウ (実機検証済み)
Tapo C210 カメラをデスク・台座の上に**正立設置（通常配置）**して使用する場合、ONVIF RelativeMove コマンドの内部回転軸と正フィードバックを合致させるため、`tapo_config.json` にて **`"INVERT_PAN": true`, `"INVERT_TILT": true` の両方を `true` に設定することが絶対必須**です。

```json
{
    "MAX_LIMIT_X": 0.96,
    "MAX_LIMIT_Y": 0.89,
    "INVERT_PAN": true,
    "INVERT_TILT": true,
    "CALIBRATED_AT": "2026-07-25 08:12:58"
}
```

> [!IMPORTANT]
> **実機テストに基づく運動極性固定ルール:**
> - **デスク・台座への正立設置 (Tapo C210 標準)**: `"INVERT_PAN": true`, `"INVERT_TILT": true` （両方 true が必須。false にすると上下逆駆動を起こし即座にフレームアウトする）
> - **天井吊り下げ (逆さ設置)**: `"INVERT_PAN": false`, `"INVERT_TILT": false`
> - **PIDチルトトルク設定**: `min_speed_y = max(0.07, min_speed * 1.8)` により、物理レンズユニットの重力抵抗を突破して上下追従の遅れを完全解消する。

## 8. PTZ 物理運動極性仕様（左右・上下と Raw ONVIF コマンドの対応関係）

本システムにおける Tapo C210 カメラの物理配置および ONVIF 通信仕様における運動極性の定義は以下の通りである。

### 1. 設置環境と設定パラメータ
- **設置方式**: デスクトップ正置 (Upright)
- **設定フラグ**: `INVERT_PAN: true`, `INVERT_TILT: true` (`camera_config.json`)

### 2. 論理移動命令と Raw ONVIF コマンドの完全対応表

| 移動目的 (物理方向) | 論理移動量 (dx, dy) | ONVIF Raw コマンド (`cmd_x`, `cmd_y`) | 物理モーター運動 |
|---|---|---|---|
| **物理左 (LEFT)** | `dx < 0` (例: `-0.15`) | `cmd_x = -dx` → **`+0.15` (プラス)** | カメラレンズが反時計回り（左）へ旋回 |
| **物理右 (RIGHT)** | `dx > 0` (例: `+0.15`) | `cmd_x = -dx` → **`-0.15` (マイナス)** | カメラレンズが時計回り（右）へ旋回 |
| **物理下 (BOTTOM)** | `dy < 0` (例: `-0.10`) | `cmd_y = dy` → **`-0.10` (マイナス)** | カメラレンズが下方へ俯く |
| **物理上 (TOP)** | `dy > 0` (例: `+0.10`) | `cmd_y = dy` → **`+0.10` (プラス)** | カメラレンズが上方へ仰ぎ見る |

> **物理アライメント（ホーム位置復帰）時のシーケンス:**
> 1. **PHASE 1 (左突き当て)**: `dx = -0.15` → Raw ONVIF `+0.15` で物理左端壁へ突き当て
> 2. **PHASE 2 (下突き当て)**: `dy = -0.10` → Raw ONVIF `-0.10` で物理下端壁へ突き当て
> 3. **PHASE 3 (中心復帰)**: `dx = +0.15` で右へ 18 歩、`dy = +0.10` で上へ 10 歩移動し、正面中心原点 `(0,0)` へ完璧に着地
